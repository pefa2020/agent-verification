# Agent Verification v3.0 — Architecture & Verification Specification

## 1. Purpose

v3.0 transitions Agent Verification from a versioned control-boundary prototype into a demonstrable agent-systems verification architecture.

The central claim is:

> An untrusted agent may propose actions, but authorization, state transition, verification, and terminal completion remain controlled by the verifier.

v3.0 does not attempt to make the agent itself trustworthy. It defines and demonstrates the boundary around the agent.

## 2. Baseline

v3.0 begins from the released v2.9 commit and preserves the v2.4–v2.9 control model.

The existing progression established:

- deterministic DFA verification;
- adversarial boundary regression tests;
- evidence integrity and replay protection;
- a verifier-owned agent/tool runtime;
- optional real LLM tool-call integration;
- an adversarial campaign against the complete known boundary.

v2.x remains frozen. v3.0 must not weaken or bypass those controls.

## 3. System Model

The system consists of four conceptual actors/components:

1. **Agent** — untrusted requester that proposes actions or tool calls.
2. **Verifier** — authoritative control layer that evaluates requests and controls state.
3. **Tools** — verifier-registered operations that execute only when authorized.
4. **Evidence** — structured verification material used to justify state progression.

The agent is never the authority for:

- whether a tool call is permitted;
- whether evidence is valid;
- whether verification passed;
- whether the DFA may transition;
- whether the run is complete.

## 4. Control State

The DFA remains the authoritative state machine:

```text
REQUEST ──valid──> BUILD ──ready──> VERIFY ──pass──> COMPLETE
   │                  │                 │
   │invalid           │blocked         │blocked
   v                  v                 v
USER_REQUIRED <───────┴─────────────────┘
   │
   │user response
   v
 BUILD

REQUEST / BUILD / VERIFY / USER_REQUIRED
        │
        └──── abort/cancel ────> ABORTED
```

`COMPLETE` and `ABORTED` are terminal states.

No v3.0 feature may create an alternate path around this DFA.

## 5. Security and Verification Invariants

### I1 — Verifier authority

Model output is advisory input, never authorization.

### I2 — State-gated execution

Tool execution is permitted only in `BUILD`.

### I3 — Tool registry control

Only verifier-registered tools may execute.

### I4 — Evidence-gated completion

The verifier reaches `COMPLETE` only through a valid verification event derived from accepted evidence.

### I5 — Evidence integrity

Accepted evidence is protected against replay, mutation, and ledger-history tampering within the defined v2.6 integrity model.

### I6 — Terminal enforcement

`COMPLETE` and `ABORTED` cannot be used as launching points for additional tool execution or ordinary DFA progression.

### I7 — USER_REQUIRED containment

An agent cannot autonomously convert `USER_REQUIRED` into authorization. A user response is required to re-enter `BUILD`.

### I8 — No direct state authority

The agent cannot directly select, assign, or skip DFA states.

### I9 — Failure containment

Tool failures and malformed model output must remain explicit failures and must not silently become successful verification evidence.

### I10 — Reproducibility

The verification experiment must be runnable deterministically without requiring network access or live credentials.

## 6. v3.0 Deliverables

v3.0 consists of four deliverables.

### D1 — Formalized control model

Document the DFA states, events, transition relation, terminal states, and invariants in a form that can be reviewed independently of implementation details.

### D2 — Verification harness

Provide executable tests that map each invariant to at least one observable assertion. Existing v2.x tests are retained; v3.0 adds explicit invariant-oriented coverage rather than duplicating adversarial cases without a purpose.

### D3 — Agent evaluation experiment

Run a controlled set of agent tasks through the runtime and record whether requested operations are allowed, denied, completed, blocked, or require user intervention.

The evaluation must include both compliant and adversarial model behavior.

### D4 — Reproducible results

Record exact commit, environment, test count, experiment inputs, outcomes, and limitations so another engineer can reproduce the result.

## 7. Non-Goals

v3.0 does not claim:

- formal mathematical proof of all possible agent behavior;
- cryptographic authenticity of external events;
- production-scale performance or availability;
- safety against every possible implementation or infrastructure failure;
- autonomous operation of unrestricted external tools;
- unrestricted code execution;
- credential management;
- a general-purpose agent framework.

These remain explicit boundaries rather than hidden assumptions.

## 8. Acceptance Criteria

v3.0 is eligible for release only when:

1. the v2.9 baseline remains intact;
2. every v3.0 invariant has executable coverage;
3. deterministic tests pass locally;
4. GitHub Actions passes on the exact release candidate commit;
5. the agent evaluation experiment is reproducible without live credentials;
6. compliant and adversarial agent behavior are both evaluated;
7. results and limitations are documented;
8. no capability is introduced that bypasses verifier authority.

## 9. Release Principle

The objective of v3.0 is not to demonstrate that an agent behaves well.

The objective is to demonstrate that the system remains controlled when the agent behaves unpredictably.
