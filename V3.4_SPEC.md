# Agent Verification v3.4 — Full Agentic AWS Verification

## Purpose

v3.4 is the integration/finalization milestone. It connects the real LLM
agent loop to the verifier-controlled AWS boundary and independently
observes the configured AWS target after deployment.

The central claim is:

> A real agent may propose actions against a real AWS test resource, but the
> verifier controls authorization, execution, observation, evidence, and
> acceptance.

## Baseline

v3.4 starts from released v3.3 and preserves the DFA, evidence integrity,
controlled software execution, deterministic build/test verification,
verifier-owned tool runtime, and bounded AWS deployment boundary.

## Full Path

```text
REAL LLM
   ↓
AGENT TOOL REQUEST
   ↓
DFA / VERIFIER
   ↓
BOUNDED AWS EXECUTOR
   ↓
REAL AWS TEST RESOURCE
   ↓
INDEPENDENT OBSERVATION
   ↓
EXPECTED vs OBSERVED STATE
   ↓
VERIFICATION EVIDENCE
   ↓
INTEGRITY LEDGER
   ↓
DFA DECISION
```

## Live AWS Scope

The initial live implementation is deliberately limited to one configured
S3 object. The verifier supplies account, region, bucket, and exact key.
The agent may supply only the bounded deployment payload.

Live AWS access is opt-in and must use ambient credentials owned by the
execution environment. Production resources are forbidden as test targets.

## Independent Observation

Deployment acknowledgement is not proof of deployment state. After a
successful PUT operation, the verifier performs an independent HEAD request
against the exact configured object and compares the observed state with the
verifier-defined expectation.

## LLM Integration

The existing OpenAI Responses API adapter is used. The model receives only
the verifier-registered `deploy` tool. Tool calls are routed through
`AgentToolRuntime`; the model cannot directly invoke boto3, choose the AWS
resource, choose the account or region, or supply credentials.

## Evidence

Deployment and observation results are structured. Deployment verification
must not be converted into overall software `VERIFY_PASS` merely because the
AWS operation succeeded. Existing evidence validation and integrity rules
remain authoritative for the overall DFA lifecycle.

## Adversarial Campaign

The integrated system must resist:

- account, region, bucket, key, target, and operation injection;
- credential injection;
- forged deployment success;
- malformed deployment responses;
- deployment failure;
- observation failure;
- forged or mismatched observed state;
- replayed and mutated evidence;
- deployment before DFA authorization;
- deployment after terminal DFA states;
- attempts to bypass the registered tool boundary;
- malformed LLM tool-call arguments;
- deterministic-test dependence on live AWS credentials.

## Live Test Isolation

Live AWS tests are explicitly opt-in through environment configuration.
The default suite must remain deterministic, network-free, and credential-free.
Live tests must use only a dedicated test bucket/object and must clean up the
created object after execution.

## Completion Criteria

v3.4 is complete when:

1. a real LLM can request the verifier-owned deployment tool;
2. the verifier gates that request through the existing runtime/DFA;
3. the bounded executor can perform the configured live AWS operation;
4. the verifier independently observes the configured AWS target;
5. expected and observed state are compared by verifier-owned logic;
6. failures cannot be converted into success by agent claims;
7. evidence remains integrity-protected;
8. integrated adversarial tests pass;
9. deterministic CI remains independent of live AWS;
10. an explicitly isolated live AWS test passes;
11. the complete repository regression suite passes;
12. the final architecture and limitations are documented.

## Finalization Principle

v3.3 established controlled deployment.
v3.4 establishes end-to-end agentic deployment verification.

After v3.4 passes its deterministic and isolated live integration gates,
the project is considered feature-complete for this research prototype.
