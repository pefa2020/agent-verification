# Agent Verification v3.2 — Software Verification Pipeline

## 1. Purpose

v3.2 extends the v3.1 controlled software execution boundary into a deterministic software verification pipeline.

The central claim is:

> Software completion is established by verifier-controlled execution evidence, not by an agent's assertion that the software works.

v3.2 defines how build and test execution becomes structured evidence that can drive the existing verifier state machine.

## 2. Baseline

v3.2 begins from the released v3.1 control boundary and preserves the v2.4–v3.1 architecture.

The existing progression established:

- deterministic DFA verification;
- adversarial boundary verification;
- evidence integrity and replay protection;
- verifier-owned agent/tool execution;
- optional real LLM tool-call integration;
- controlled workspace and software execution;
- fixed verifier-owned build and test commands.

No v3.2 feature may bypass verifier authority or weaken the v3.1 executor boundary.

## 3. System Model

The verification pipeline contains:

1. **Agent** — proposes software changes and may request verification operations.
2. **Verifier** — authorizes operations, owns state, evaluates evidence, and controls completion.
3. **Executor** — performs only verifier-defined build/test operations inside the controlled workspace.
4. **Verification Record** — structured result describing what was executed and whether it succeeded.
5. **Evidence** — accepted verification material used to drive DFA progression.

The agent is never authoritative for:

- whether a build passed;
- whether tests passed;
- whether evidence is valid;
- whether verification succeeded;
- whether the DFA may reach COMPLETE.

## 4. Verification Lifecycle

The intended lifecycle is:

```text
REQUEST
   ↓
BUILD
   ↓
software changes
   ↓
RUN_BUILD
   ↓
RUN_TESTS
   ↓
structured verification result
   ↓
validated evidence
   ↓
VERIFY
   ├── PASS ──> COMPLETE
   ├── FAIL ──> controlled failure / repair input
   └── USER_REQUIRED
```

`COMPLETE` remains terminal.

A failed build or failed test run must never be converted into successful verification evidence by the agent.

## 5. Verification Result Contract

Each pipeline execution must produce a structured result containing, at minimum:

- operation name;
- success status;
- return code when applicable;
- executed command identity;
- captured output or a bounded representation of it;
- explicit error information when unsuccessful.

The result must distinguish:

- execution failure;
- command failure;
- successful execution;
- successful verification.

A successful process exit is necessary for the corresponding execution step but is not by itself permission for the agent to claim overall software completion.

## 6. Evidence Contract

Verification evidence must be derived from executor-observed results rather than free-form agent claims.

Accepted evidence must identify the verification outcome and preserve the existing v2.6 evidence-integrity model.

Evidence processing must:

- validate its schema;
- reject malformed evidence;
- reject replay according to the existing ledger rules;
- reject tampered history;
- preserve explicit failures;
- produce the DFA event corresponding to the validated outcome.

The pipeline must not accept a model-generated statement such as `tests passed` as equivalent to executor-produced test evidence.

## 7. Build/Test Ordering

The default verification sequence is:

1. execute the verifier-defined build command;
2. if build fails, record an explicit build failure and do not report successful verification;
3. execute the verifier-defined test command when the pipeline policy permits it;
4. record the observed result;
5. construct verification evidence from those observations;
6. submit evidence through the existing verifier boundary;
7. allow the DFA to determine the resulting state.

The implementation must not allow callers to replace the configured commands with arbitrary commands through request arguments.

## 8. Failure Containment

Failure is first-class state information.

The pipeline must preserve:

- non-zero process exit codes;
- process launch failures;
- timeouts;
- malformed result data;
- missing or invalid evidence;
- tool execution errors.

No failure may silently become a successful verification result.

If verification cannot establish success, the system must not reach `COMPLETE` through the verification pipeline.

## 9. Verification Invariants

### V1 — Executor authority

Build and test commands originate from verifier configuration, not agent-supplied command strings.

### V2 — Observed-result authority

Verification status is derived from executor-observed results rather than agent assertions.

### V3 — Build failure containment

A failed build cannot produce successful verification evidence.

### V4 — Test failure containment

A failed test run cannot produce successful verification evidence.

### V5 — Evidence validation

Malformed or structurally invalid verification evidence is rejected.

### V6 — Evidence integrity

Verification evidence remains subject to replay and tamper protection provided by the existing integrity ledger.

### V7 — State-gated verification

Verification operations remain subject to the verifier-controlled DFA lifecycle.

### V8 — Terminal enforcement

`COMPLETE` and `ABORTED` cannot be used to launch additional verification operations.

### V9 — Agent non-authority

The agent cannot directly select a PASS outcome or force the DFA into `COMPLETE`.

### V10 — Reproducibility

The verification pipeline is runnable deterministically without AWS credentials, live cloud infrastructure, or network-dependent services.

## 10. Adversarial Requirements

v3.2 must include executable tests for at least:

- agent-forged successful verification;
- forged PASS evidence after a failed build;
- forged PASS evidence after failed tests;
- replacement of configured build commands;
- replacement of configured test commands;
- malformed verification results;
- malformed evidence;
- replayed evidence;
- tampered evidence history;
- verification attempted before authorization;
- verification attempted after COMPLETE;
- verification attempted after ABORTED;
- deterministic repeated verification.

## 11. Deliverables

### D1 — Verification pipeline contract

Document the structured execution-result and verification-evidence contracts.

### D2 — Executable verification pipeline

Provide a verifier-owned pipeline that converts controlled build/test execution into structured verification evidence.

### D3 — Adversarial verification tests

Map the v3.2 invariants and attack cases to executable assertions.

### D4 — Reproducible results

Record exact commit, environment, test count, verification scenarios, outcomes, and limitations.

## 12. Non-Goals

v3.2 does not introduce:

- AWS deployment;
- live cloud verification;
- production infrastructure;
- unrestricted shell execution;
- unrestricted package installation;
- arbitrary network access;
- credential management;
- autonomous external side effects;
- formal mathematical proof of all possible agent behavior;
- production-scale performance claims.

Those concerns remain future milestones.

## 13. Acceptance Criteria

v3.2 is eligible for release only when:

1. the v3.1 baseline remains intact;
2. structured build/test verification results are implemented;
3. verification evidence is derived from executor observations;
4. build and test failures remain explicit failures;
5. forged PASS claims are rejected;
6. evidence replay and tampering remain rejected;
7. verification remains DFA-gated;
8. terminal states remain enforced;
9. deterministic adversarial tests pass locally;
10. GitHub Actions passes on the exact release candidate commit;
11. results and limitations are documented;
12. no capability bypasses verifier authority.

## 14. Release Principle

v3.1 demonstrated that software can be executed under a controlled boundary.

v3.2 must demonstrate that the system—not the agent—determines whether that software has passed verification.
