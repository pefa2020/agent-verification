# Agent Verification v3.1 — Controlled Software Executor Specification

## 1. Purpose

v3.1 extends the verifier from a demonstrated agent/tool boundary into a controlled software-execution environment.

The objective is to allow an untrusted agent to create and modify software inside a verifier-owned workspace while preserving verifier authority over every executable operation.

The central rule remains:

> The agent may propose an operation, but the verifier decides whether that operation may execute.

v3.1 does not introduce unrestricted autonomous execution, AWS access, credential management, or unrestricted shell access.

## 2. Baseline

v3.1 begins from the released v3.0 architecture and preserves all v2.4–v3.0 controls.

Existing guarantees remain mandatory:

- deterministic DFA control;
- verifier-owned authorization;
- registered-tool enforcement;
- evidence validation;
- evidence integrity and replay protection;
- terminal-state enforcement;
- USER_REQUIRED containment;
- adversarial regression coverage;
- deterministic reproducibility.

v3.1 must not create an alternate execution path around these controls.

## 3. System Model

The system contains:

1. **Agent** — untrusted requester that proposes software operations.
2. **Verifier** — authoritative authorization and state-control layer.
3. **Executor** — constrained implementation layer that performs only authorized operations.
4. **Workspace** — verifier-owned software directory.
5. **Evidence** — structured records proving execution and verification outcomes.

The agent does not directly control the executor or filesystem.

## 4. Workspace Boundary

The executor operates inside a designated workspace.

The executor must reject attempts to:

- access files outside the workspace;
- escape the workspace through `..`;
- follow unauthorized paths outside the workspace;
- modify verifier source or protected control files unless explicitly authorized;
- write outside the configured workspace root.

Path resolution must produce a canonical path before authorization and execution.

The workspace boundary is enforced by the executor, not by agent instructions.

## 5. Initial Tool Contract

v3.1 introduces only the following controlled operations:

### READ_FILE

Read a file inside the authorized workspace.

### WRITE_FILE

Replace the contents of an existing file inside the workspace.

### CREATE_FILE

Create a new file inside the workspace.

### DELETE_FILE

Delete a file inside the workspace when explicitly authorized.

### RUN_TESTS

Execute the configured project test command through the controlled executor.

### RUN_BUILD

Execute the configured project build command through the controlled executor.

Every operation is represented as an explicit tool request and passes through the verifier-owned runtime.

## 6. Execution Rules

### 6.1 State gating

Software execution is permitted only in `BUILD`.

Requests made in:

- `REQUEST`;
- `VERIFY`;
- `USER_REQUIRED`;
- `COMPLETE`;
- `ABORTED`

must not execute.

### 6.2 Tool registry

Only verifier-registered operations may execute.

Unknown tool names are rejected.

### 6.3 Argument validation

Tool arguments must satisfy the executor's schema before execution.

Malformed arguments are rejected.

### 6.4 Workspace enforcement

Every file operation must resolve inside the authorized workspace.

### 6.5 Command enforcement

`RUN_TESTS` and `RUN_BUILD` may invoke only commands explicitly configured by the verifier.

Arbitrary shell commands are outside v3.1 scope.

### 6.6 Failure containment

Execution failures must become explicit failure results.

A failed operation cannot be silently converted into successful verification evidence.

## 7. Protected Resources

The executor must maintain a protected-resource boundary.

At minimum, v3.1 protects:

- verifier control logic;
- DFA implementation;
- evidence-integrity implementation;
- executor authorization logic;
- verification configuration.

An agent request to modify a protected resource must be rejected unless a future version explicitly introduces a controlled mechanism for doing so.

## 8. Verification Pipeline

The v3.1 software lifecycle is:

```text
REQUEST
  ↓
authorization
  ↓
BUILD
  ↓
software modification
  ↓
RUN_BUILD
  ↓
RUN_TESTS
  ↓
VERIFY
  ↓
evidence
  ↓
COMPLETE / USER_REQUIRED / ABORTED
```

Completion remains controlled by the verifier.

The executor cannot declare verification success.

## 9. Evidence

The executor must provide structured results describing:

- operation;
- authorized/denied outcome;
- success/failure;
- command or file target;
- relevant output;
- error information;
- execution ordering.

Verification evidence remains subject to the existing v2.6 integrity model.

The agent cannot directly manufacture accepted evidence.

## 10. Adversarial Requirements

v3.1 must test at least:

1. path traversal;
2. absolute-path escape;
3. access outside workspace;
4. protected-file modification;
5. unknown tool request;
6. malformed tool arguments;
7. build command substitution;
8. arbitrary-shell request;
9. execution before BUILD;
10. execution after COMPLETE;
11. execution after ABORTED;
12. execution during USER_REQUIRED;
13. tool failure propagation;
14. evidence forgery;
15. evidence replay;
16. repeated deterministic execution.

Any unauthorized execution is release-blocking.

## 11. Deterministic Requirements

The v3.1 verification suite must run without:

- AWS credentials;
- external network access;
- live LLM access;
- cloud infrastructure.

The executor must use deterministic fixtures for its release-gate tests.

Live infrastructure testing belongs to a later milestone.

## 12. Release Acceptance Criteria

v3.1 is release eligible only when:

1. the v3.0 baseline remains intact;
2. the workspace boundary has executable coverage;
3. all initial tool operations have executable authorization tests;
4. arbitrary shell execution is rejected;
5. protected-resource access is rejected;
6. build and test operations are verifier-authorized;
7. failure results remain explicit;
8. adversarial tests pass;
9. deterministic reproducibility is demonstrated;
10. the full regression suite passes;
11. GitHub Actions passes on the exact release candidate commit;
12. results and limitations are documented.

## 13. Non-Goals

v3.1 does not provide:

- unrestricted shell execution;
- arbitrary code execution outside the workspace;
- AWS deployment;
- AWS credentials;
- production infrastructure;
- network-enabled autonomous execution;
- unrestricted package installation;
- autonomous external side effects;
- formal proof of all possible executor failures.

These capabilities require additional verification boundaries in later versions.

## 14. Architectural Principle

The purpose of v3.1 is not merely to let an agent edit code.

It is to demonstrate that an agent can be given meaningful software-building capability while remaining subordinate to a verifier that controls what it may execute.
