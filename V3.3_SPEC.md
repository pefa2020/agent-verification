# Agent Verification v3.3 — AWS Deployment Boundary

## 1. Purpose

v3.3 extends the verifier-controlled architecture with a bounded AWS deployment boundary.

The central claim is:

> An agent may propose a deployment, but the verifier—not the agent—controls which AWS operation may execute, which target may be addressed, and whether deployment success is accepted as evidence.

v3.3 introduces deployment capability without weakening the v2.4–v3.2 control model.

## 2. Baseline

v3.3 begins from the released v3.2 commit and preserves the existing architecture:

- deterministic DFA verification;
- adversarial boundary regression tests;
- evidence integrity and replay protection;
- verifier-owned agent/tool runtime;
- optional real LLM tool-call integration;
- controlled software execution;
- deterministic build/test verification;
- evidence conversion through the existing verifier boundary.

Previous releases remain frozen. No v3.3 feature may bypass verifier authority.

## 3. System Model

The deployment path consists of five conceptual components:

1. **Agent** — proposes a deployment operation and target.
2. **Verifier** — authorizes the operation according to the DFA and deployment policy.
3. **Deployment Executor** — performs only verifier-approved AWS operations.
4. **AWS Target** — the explicitly configured deployment environment/resource.
5. **Deployment Evidence** — structured, executor-observed evidence describing the operation and result.

The agent is never authoritative for:

- which AWS account or region may be targeted;
- which resource may be modified;
- whether credentials are valid or sufficient;
- whether deployment occurred;
- whether deployment passed verification.

## 4. Deployment Boundary

The first v3.3 implementation must use an explicit allowlist rather than an unrestricted AWS API or shell interface.

The deployment executor must enforce, at minimum:

- configured AWS account identity;
- configured AWS region;
- configured deployment environment/resource identity;
- fixed operation types;
- explicit timeouts;
- structured success/failure results.

The agent must not be able to replace the executor command, arbitrary AWS API method, target account, region, or protected resource through ordinary tool arguments.

## 5. Initial Capability Scope

v3.3 is intentionally limited to a small deployment operation surface suitable for deterministic testing.

The implementation should support a verifier-selected deployment operation against a verifier-selected AWS target. The concrete AWS service and resource type must be explicitly configured by the verifier and must not be inferred from unrestricted agent input.

No unrestricted AWS client wrapper is permitted.

## 6. Authorization Flow

The intended lifecycle is:

```text
REQUEST
   ↓
BUILD
   ↓
software verification
   ↓
DEPLOYMENT REQUEST
   ↓
verifier authorization
   ↓
AWS deployment executor
   ↓
deployment result
   ↓
validated deployment evidence
   ↓
VERIFY
```

The deployment capability must remain subject to the existing state-gating model. Deployment must not become an alternate path to `COMPLETE`.

## 7. Deployment Result Contract

Every deployment operation must return a structured result containing, at minimum:

- operation name;
- success/failure status;
- target identity;
- AWS account identity used or observed;
- AWS region;
- bounded textual output/details;
- explicit error information;
- return/status information where available.

A deployment result must represent executor-observed state, not an agent assertion.

## 8. Deployment Evidence

Deployment evidence must:

1. be constructed from executor-observed results;
2. include a unique run identifier;
3. bind the result to the repository commit or deployment artifact identity where available;
4. identify the configured deployment target;
5. distinguish PASS, FAIL, and BLOCKED outcomes;
6. pass through the existing evidence validation boundary;
7. pass through the existing evidence integrity ledger;
8. drive DFA transitions only through the existing evidence-to-event mapping.

A successful deployment alone must not imply full verification when integration or smoke criteria remain incomplete.

## 9. Credentials

v3.3 may use existing AWS credential mechanisms available to the execution environment, but credential handling is outside the agent's authority.

The agent must never receive unrestricted credential material through tool arguments, generated files, model-visible output, or arbitrary shell execution.

CI and deterministic tests must not require live AWS credentials unless a test is explicitly marked as an optional live integration test.

## 10. Security and Verification Invariants

### D1 — Verifier-selected target

The agent cannot choose an arbitrary AWS account, region, environment, or protected resource.

### D2 — Verifier-selected operation

Only deployment operations explicitly registered by the verifier may execute.

### D3 — State-gated deployment

Deployment execution is permitted only from an authorized DFA state and cannot be launched from terminal states.

### D4 — Executor authority

Deployment success or failure is determined from executor-observed results, never from model claims.

### D5 — Failure containment

AWS errors, authorization failures, timeouts, and malformed responses remain explicit deployment failures.

### D6 — Evidence validation

Malformed, contradictory, or incomplete deployment evidence cannot advance verification.

### D7 — Evidence integrity

Accepted deployment evidence remains subject to replay protection and tamper-evident ledger verification.

### D8 — Credential boundary

The agent cannot directly access or substitute AWS credentials.

### D9 — No unrestricted AWS interface

The deployment boundary does not expose a general-purpose AWS API or arbitrary shell command to the agent.

### D10 — Reproducibility

The full deterministic test suite remains runnable without live AWS credentials or network access.

## 11. Adversarial Requirements

v3.3 must test at least:

- alternate AWS account injection;
- alternate region injection;
- unauthorized target/resource injection;
- unauthorized operation injection;
- command/API replacement;
- malformed deployment responses;
- executor-reported deployment failure presented as success;
- forged deployment success evidence;
- replayed deployment evidence;
- mutated deployment evidence;
- deployment requests before authorization;
- deployment after `COMPLETE`;
- deployment after `ABORTED`;
- credential argument injection;
- deterministic repeated execution without live AWS access.

## 12. Non-Goals

v3.3 does not claim:

- production AWS deployment automation;
- unrestricted multi-service AWS access;
- unrestricted IAM administration;
- arbitrary credential management;
- arbitrary shell execution;
- production infrastructure resilience;
- live-system integration verification;
- smoke verification against deployed software;
- formal security proof.

Those capabilities belong to later, separately verified milestones.

## 13. Acceptance Criteria

v3.3 is eligible for release only when:

1. the v3.2 baseline remains intact;
2. deployment authorization is verifier-controlled;
3. the AWS deployment boundary is explicitly allowlisted;
4. deployment results are structured and executor-observed;
5. deployment evidence uses the existing validation/integrity/DFA path;
6. every v3.3 invariant has executable coverage;
7. adversarial deployment-boundary tests pass;
8. deterministic tests pass locally without live AWS credentials;
9. GitHub Actions passes on the exact release candidate commit;
10. limitations and live-AWS test requirements are documented.

## 14. Release Principle

v3.3 does not attempt to make the agent trustworthy.

It makes deployment controllable.

The agent may request a deployment, but only the verifier-owned boundary determines whether, where, and how that deployment can occur.
